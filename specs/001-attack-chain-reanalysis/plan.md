# Implementation Plan: Attack Chain Counterfactual Re-analysis

**Branch**: `001-attack-chain-reanalysis` | **Date**: 2026-09-07 | **Spec**: [spec.md](spec.md)
**Constitution**: [.specify/memory/constitution.md](../../.specify/memory/constitution.md)

---

## Summary

A single-page app on Vercel. A Vite + React frontend renders an attack chain with React Flow.
A Python serverless function holds the Anthropic key and runs analysis with Claude Sonnet 5 using
structured output. The bundled scenario, its answer key, and the cached first analysis are static
JSON committed to the repo. Every user intervention becomes a list of removed event IDs sent to
the API, which subtracts them from the bundled scenario and re-analyzes live. Citation validation
and diffing run in the browser in plain TypeScript so they are unit-testable without a server.

| Decision | Choice | Why |
|---|---|---|
| Backend | Python 3.12 on Vercel Python functions, FastAPI | User choice. Vercel has no Java runtime, so the Spring Boot scaffold is removed. |
| Frontend | Vite + React 18 + TypeScript | React Flow needs React. Vite is the lightest path to a static build Vercel serves natively. |

## Architecture

```
Browser (Vite + React)                          Vercel Python function
+-----------------------------+                 +-----------------------------+
| public/scenarios/<id>/      |                 | api/index.py  (FastAPI)     |
|   events.json      (static) |                 |   POST /api/analyze         |
|   answer_key.json  (static) |                 |     load data/scenarios/    |
|   analysis.json    (static) |                 |     subtract removed ids    |
|                             |  removed ids    |     Claude Sonnet 5, parse  |
| src/lib/validate.ts         | --------------> |     return AnalyzeResponse  |
| src/lib/intervene.ts        | <-------------- |                             |
| src/lib/diff.ts             | AnalyzeResponse |   GET /api/health           |
| src/graph/*  (React Flow)   |                 +-----------------------------+
+-----------------------------+                            |
                                                           v
                                                  Anthropic API (key in env)
```

Request flow for an intervention:

1. User clicks "Isolate" on a node or "Block" on an edge.
2. `intervene.ts` computes the event IDs to remove and unions them with any prior removals.
3. Client POSTs `{ scenario_id, removed_event_ids }`.
4. Server validates IDs against the bundled scenario, subtracts, builds the prompt, calls Claude.
5. Client receives the new chain, runs `validate.ts`, runs `diff.ts` against the previous chain,
   re-renders with the diff styles. Previous chain stays on screen until the new one arrives.

## Data model

### Event (`events.json` is an array of these)

```ts
type EventType = "process_start" | "network_connection" | "authentication" | "file_access";

interface Event {
  id: string;          // "E-0001" .. "E-0500", assigned in timestamp order, unique
  timestamp: string;   // ISO 8601 UTC, events sorted ascending
  source: string;      // asset name: a user, a host, or an external address
  target: string;      // asset name
  type: EventType;
  detail: string;      // one line, e.g. "powershell.exe -enc <base64> spawned by OUTLOOK.EXE"
}
```

This is exactly what the generator emits. There is no `user` field: users are assets and
appear as `source` (for example `jsmith -> WKSTN-042` for a process start, or
`administrator -> FILESRV-01` for a file access).

Asset kind is derived by regex, never stated by the model:

| Kind | Rule | Examples |
|---|---|---|
| external | starts with a digit | `203.0.113.47`, `151.101.1.140 (fastly-cdn)` |
| host | uppercase with a hyphenated number | `WKSTN-042`, `FILESRV-01`, `DC-01` |
| user | anything else (lowercase identifiers) | `jsmith`, `administrator`, `svc_backup` |

Generator invariants the plan relies on, from the skill's own contract: every seeded event
names two distinct assets; attacker IPs never appear in noise; attack hosts and users are
reused in benign noise so the chain cannot be found by name alone; seeded ids are scattered.

### Answer key (as generated)

```ts
interface AnswerKey {
  scenario_id: string;             // "attack-chain-01" | "benign-lookalike-02"
  scenario_name: string;
  scenario_type: "attack" | "benign";
  correct_answer: string;          // "one attack chain" | "no attack"
  total_events: number;
  attack_event_ids: string[];      // 16 for attack-chain-01, [] for the benign scenario
  assets_involved?: string[];      // attack scenario
  chain_summary?: string[];        // attack scenario: six plain-English steps
  lookalike_event_ids?: string[];  // benign scenario
  lookalikes?: { id: string; why_benign: string }[];  // benign scenario
  note: string;
}
```

### Chain (server response and cached analysis; Pydantic on the server, zod on the client)

Two names, one shape family. `ChainOutput` is what the model returns. `AnalyzeResponse` wraps it
with the server-added fields and is the only chain shape that crosses the wire or is written
to `analysis.json`. The TypeScript alias `Chain` means `AnalyzeResponse`.

```ts
interface ChainNode { id: string; label: string; }   // id is the asset name, verbatim
interface ChainEdge {
  source: string;
  target: string;
  action: string;        // 3 to 6 words, e.g. "logged in from outside"
  description: string;   // one plain-English sentence
  citations: string[];   // event ids
}
interface ChainOutput {  // model output, Pydantic `ChainOutput` on the server
  nodes: ChainNode[];
  edges: ChainEdge[];
  summary: string;       // at most two sentences, plain English
}
interface AnalyzeResponse extends ChainOutput {   // TS alias: Chain
  scenario_id: string;
  removed_event_ids: string[];   // deduplicated, in the order first seen
  prompt_version: string;        // server's PROMPT_VERSION constant
}
```

`analysis.json` is an `AnalyzeResponse` with `removed_event_ids: []`.

### Validated and diffed chain (client only, frozen so the validate, diff, and graph work agree)

```ts
interface CitationCheck { id: string; exists: boolean; involvesBothEndpoints: boolean; }
interface ValidatedEdge extends ChainEdge {
  verified: boolean;              // citations.length > 0 && every check passes
  checks: CitationCheck[];
  bannedWords: string[];          // "secure", "safe", "contained" found in action or description
}
interface ValidatedChain {
  scenario_id: string;
  removed_event_ids: string[];
  prompt_version: string;
  nodes: ChainNode[];             // model nodes, minus any whose id appears in no event
  edges: ValidatedEdge[];         // model edges, minus any whose endpoint appears in no event
  summary: string;
  warnings: string[];             // one line per dropped node or edge, for the console and tests
}

type DiffStatus = "survived" | "vanished" | "appeared";
interface DiffedEdge extends ValidatedEdge { status: DiffStatus; }
interface DiffedNode extends ChainNode   { status: DiffStatus; }
interface DiffedChain {
  nodes: DiffedNode[];            // union of previous and current nodes
  edges: DiffedEdge[];            // union of previous and current edges
  summary: string;                // current summary
  counts: { vanished: number; survived: number; appeared: number };   // edges only
}
```

Edge identity for diffing is `${source}->${target}`. Node identity is `id`. Action and label text
are not part of identity. A vanished edge or node carries its previous data. The first render,
with no previous chain, is a `DiffedChain` where everything is `survived`.

## Wire contract (frozen)

This section is the whole agreement between the backend agent and the frontend agent. Each
agent builds and tests against it alone. Nobody changes it by editing code: change this
section first, then the examples in `specs/001-attack-chain-reanalysis/contract/`, then both
test suites, then code.

### Ownership

| Owns | Files |
|---|---|
| Backend agent | `api/**`, `scripts/analyze.py`, `requirements.txt`, the `functions` block of `vercel.json`, `data/scenarios/*/analysis.json` |
| Frontend agent | `src/**`, `tests/**`, `package.json`, `vite.config.ts`, `scripts/copy_scenarios.mjs`, the `rewrites` block of `vercel.json` |
| Shared, read only | this section, `contract/*.json` examples, `data/scenarios/*/events.json` and `answer_key.json` (generator output), `.env.example` |

### Shapes

```ts
interface AnalyzeRequest {
  scenario_id: string;
  removed_event_ids: string[];    // may be empty: a full analysis of the bundled scenario
}

// AnalyzeResponse: see Data model. Alias Chain on the client.

interface ErrorResponse {
  error: ErrorCode;
  detail: string;                 // one plain-English sentence for the banner
  ids?: string[];                 // only for unknown_event_ids
}

type ErrorCode =
  | "unknown_scenario" | "unknown_event_ids" | "too_many_removed" | "bad_request"
  | "rate_limited" | "not_configured" | "model_refused" | "model_error" | "internal";

interface HealthResponse {
  ok: true;
  live: boolean;                  // false when ANTHROPIC_API_KEY is unset
  model: string;                  // "claude-sonnet-5"
}
```

Field names are `snake_case` on the wire and in TypeScript. Nothing is renamed at the boundary.
Unknown fields in a response are stripped by zod, never rejected, so the server may add fields
without breaking the client. Unknown fields in a request are ignored by the server.

### Endpoints

| Endpoint | Request | 200 body | Notes |
|---|---|---|---|
| `POST /api/analyze` | `AnalyzeRequest`, JSON | `AnalyzeResponse` | Calls the model. 8 to 25 seconds. |
| `GET /api/health` | none | `HealthResponse` | Never calls the model. Called once on page load. |

Server rules for `POST /api/analyze`, in the order they are checked:

1. Body must parse as `AnalyzeRequest`, else `bad_request`.
2. `scenario_id` must be a bundled scenario, else `unknown_scenario`.
3. `removed_event_ids` is deduplicated, preserving first-seen order.
4. Every id must exist in the scenario, else `unknown_event_ids` with `ids` listing the bad ones.
5. At most 200 ids after deduplication, else `too_many_removed`.
6. Per-instance token bucket, 10 calls per minute, else `rate_limited`.
7. `ANTHROPIC_API_KEY` must be set, else `not_configured`.
8. Model call. Refusal is `model_refused`. Any SDK error, timeout, or unparseable output is
   `model_error`.
9. Response echoes `scenario_id`, the deduplicated `removed_event_ids`, and `prompt_version`.

### Status codes

Every non-2xx response body is an `ErrorResponse`, including the ones FastAPI would otherwise
generate itself. The backend installs handlers for `RequestValidationError` (to `bad_request`)
and for any uncaught `Exception` (to `internal`) so the client sees one error shape.

| `error` | HTTP | `detail` example |
|---|---|---|
| `bad_request` | 400 | "Request body must have scenario_id and removed_event_ids." |
| `unknown_scenario` | 404 | "No scenario named nope." |
| `unknown_event_ids` | 400 | "2 event ids are not in this scenario." plus `ids` |
| `too_many_removed` | 400 | "At most 200 events can be removed." |
| `rate_limited` | 429 | "Too many analyses in the last minute. Try again shortly." |
| `not_configured` | 503 | "Live re-analysis is off: the server has no model key." |
| `model_refused` | 502 | "The model declined to analyse these events." |
| `model_error` | 502 | "The model call failed or timed out." |
| `internal` | 500 | "Something went wrong on the server." |

The client parses the body of any non-2xx response as `ErrorResponse`. If even that fails, the
client synthesises `{error: "internal", detail: "Unexpected response from the server."}`. The
banner shows `detail` verbatim. `not_configured` additionally disables the intervention buttons
and flips the live pill, the same as `live: false` from health.

### Routing

- FastAPI declares routes with the full path: `/api/analyze`, `/api/health`.
- Locally: `uvicorn api.index:app --port 8000`, and `vite.config.ts` proxies `/api` to it.
- On Vercel: `vercel.json` rewrites `/api/(.*)` to `/api/index`. Whether the function sees the
  original path or the rewritten one is on the first-deploy verification list. If it sees
  `/api/index`, the backend adds a catch-all that dispatches on the original URL header.
- Same origin everywhere, so no CORS headers.

### Static files

The prebuild step copies `data/scenarios/` to `public/scenarios/`. The client fetches, relative
to the site root:

| Path | Shape | If missing |
|---|---|---|
| `/scenarios/<id>/events.json` | `Event[]` | Fatal. The page shows a load error. |
| `/scenarios/<id>/answer_key.json` | `AnswerKey` | Fatal. |
| `/scenarios/<id>/analysis.json` | `AnalyzeResponse` | Not fatal. `cached` is `null`; the graph is empty and the toolbar offers "Analyse" which posts `removed_event_ids: []`. |

The zod `AnswerKey` schema strips fields the client does not use (`seed`, `generated_by`,

## Analysis design (server)

### Prompts

The model receives exactly two pieces of text on every call: a frozen system prompt and a user
message that is the remaining event list. Both live in `api/analysis.py` as constants next to
the Pydantic models, so the cached `analysis.json` and the live path are produced by the same
text. `PROMPT_VERSION` is written into every `analysis.json`; the cached-analysis test fails if
it does not match the current constant, which forces a regeneration when the prompt changes.

The model is never told that events were removed, what the user did, or what the previous chain
looked like. It sees only the remaining events. That is what makes the re-analysis honest: the
new chain is built from evidence, not from a description of the intervention.

#### System prompt (`SYSTEM_PROMPT`, frozen, `cache_control` ephemeral)

```text
You are a security analyst. You will be given a list of telemetry events from one
organisation's network over one day. Most events are ordinary activity. Some of them may
together form a single attack. Your job is to find the attack, if there is one, and describe it
as a chain of actions between assets, for a reader who has no security background.

Each event line has this shape:
  <id> | <timestamp> | <source> -> <target> | <type> | <detail>
The source and target are asset names. An asset is a host (for example WKSTN-042), a user
account (for example jsmith), or an external address (for example 203.0.113.47). User accounts
are assets in their own right: "jsmith -> WKSTN-042" means the user jsmith did something on
that workstation.

Return a chain with these rules.

Nodes
- A node is an asset. Its id must be an asset name copied exactly as it appears in the events,
  including any label in parentheses. Never invent, shorten, or normalise a name.
- Include only assets that take part in the attack. Leave out assets that appear only in
  ordinary activity.
- Every asset you use as the source or target of an edge must also appear in this node list.
  Never draw an edge to or from an asset you have not listed. This includes external addresses
  that only receive data.
- The label is a short plain-English description of the asset's role, at most four words,
  based only on what the events show. Example: "finance file server".

Edges
- An edge is one attacker action from a source asset to a target asset.
- Every edge must list the ids of the events that justify it in "citations". Each cited event
  must have exactly the edge's source as its source and exactly the edge's target as its
  target. If the events that show an action run from a user to a host, the edge runs from that
  user to that host, not from the host the user was sitting at.
- Never cite an id that is not in the list. Never leave citations empty.
- Prefer fewer, well-supported edges over many weak ones. One edge may cite several events.
- Order edges by the timestamp of their earliest cited event.
- "action" is three to six words naming what happened, for example "logged in from outside"
  or "copied files out". "description" is one sentence a newcomer can follow, and may say why
  this step matters for the next one.

Summary
- At most two sentences. Say what the evidence shows happened, from first step to last.

If the events do not show a connected attack, return no edges, list no nodes, and use the
summary to say that the remaining events do not show a connected attack.

Wording
- Plain English throughout. Do not use security jargon or technique names in "action",
  "description", or "summary". If you must refer to a technique, describe what it did.
- Never use the words "secure", "safe", or "contained".
- Do not give scores, percentages, confidence levels, or severity ratings.
- Do not speculate beyond the events. Say only what the cited events support.
```

Roughly 550 tokens. This is likely below the minimum cacheable prefix for the model, so the
`cache_control` marker may be a no-op. It costs nothing and becomes useful if the prompt grows.

#### User message (`render_events(events)`)

One header line, then one line per remaining event in timestamp order. Asset names are copied
verbatim from `events.json`, including parenthesised labels, so the model can copy them back.

```text
Events: 486 of the day's telemetry records, in time order.

E-0001 | 2026-09-05T07:31:00Z | rgarcia -> WKSTN-017 | authentication | Interactive logon succeeded
E-0002 | 2026-09-05T07:31:00Z | WKSTN-017 -> 151.101.1.140 (fastly-cdn) | network_connection | HTTPS to CDN
...
E-0500 | 2026-09-05T17:29:00Z | svc_backup -> FILESRV-02 | file_access | Scheduled backup read
```

The count in the header changes per call, which is fine because the user message sits after
the cache breakpoint. No other text is added. In particular the message never lists the
removed ids, never says "re-analyse", and never includes the previous chain.

#### What the prompt deliberately leaves to code

| Concern | Why it is not in the prompt |
|---|---|
| Citation validity | Code checks it after the fact (`validate.ts`). The prompt asks for it, code enforces it. |
| Asset kind (host, user, external) | Derived by regex on the client. The model is never asked to classify names. |
| Banned words in model output | A client-side check in `validate.ts` flags them so the test suite can catch a prompt regression. |
| Diff, survived and vanished edges | Computed by `diff.ts` from two chains. The model never sees the previous chain. |
| Removed events | Subtracted by the server before rendering. The model sees only what remains. |

#### Expected shape on the full scenario

With all 500 events the prompt should produce the seven nodes in the answer key and seven or
eight edges matching the table in the Scenarios section. Task T012 checks this by hand before
committing `analysis.json`. If the model draws host-to-host edges and cites user-to-host events,
the citations fail the endpoint check; the fix is to strengthen the "user accounts are assets"
paragraph, not to relax validation.

### Call

```python
from pydantic import BaseModel
import anthropic

class ChainEdge(BaseModel):
    source: str
    target: str
    action: str
    description: str
    citations: list[str]

class ChainNode(BaseModel):
    id: str
    label: str

class ChainOutput(BaseModel):
    nodes: list[ChainNode]
    edges: list[ChainEdge]
    summary: str

class AnalyzeResponse(ChainOutput):
    scenario_id: str
    removed_event_ids: list[str]
    prompt_version: str

client = anthropic.Anthropic()  # ANTHROPIC_API_KEY from env

response = client.messages.parse(
    model="claude-sonnet-5",
    max_tokens=8000,
    thinking={"type": "adaptive"},
    output_config={"effort": "medium"},
    system=[{"type": "text", "text": SYSTEM_PROMPT, "cache_control": {"type": "ephemeral"}}],
    messages=[{"role": "user", "content": render_events(remaining)}],
    output_format=ChainOutput,
)
if response.stop_reason == "refusal":
    raise ModelRefused(response.stop_details)
chain = response.parsed_output
```

The server wraps the output in `AnalyzeResponse`, adding `scenario_id`, the deduplicated
`removed_event_ids`, and `PROMPT_VERSION`. The same function is used by `scripts/analyze.py` to produce the cached `analysis.json`, so the cached and live paths
cannot drift.

### Latency and timeouts

Expect 8 to 25 seconds per call. `vercel.json` sets `maxDuration: 60` for `api/**`. The SDK
client is constructed with `timeout=50.0, max_retries=0` so a slow call fails inside the
function limit with a clean `model_error` rather than a platform timeout. Streaming is not
needed at this output size.

### Guards

- In-memory token bucket per function instance: 10 calls per minute. Weak across instances,
  but it is a demo. Returns `rate_limited` 429.
- `MAX_REMOVED = 200`.
- If `ANTHROPIC_API_KEY` is unset, `/api/health` reports `live: false` and `/api/analyze`
  returns 503 `not_configured`. The UI disables intervention buttons and says why.
- `RequestValidationError` and uncaught exceptions are converted to the `ErrorResponse` shape
  (`bad_request` 400, `internal` 500) so no FastAPI default body ever reaches the client.

## Frontend design

### Layout

Three regions. Left 70 percent: the graph with a toolbar above it (scenario title, Reset,
live status pill, Answer key toggle). Right 30 percent: evidence panel, empty until an edge is
clicked. A legend sits in the bottom-left corner of the graph.

### Graph

- React Flow with custom node and edge components. Layout computed once per chain with dagre,
  `rankdir: "LR"`, `nodesep: 40`, `ranksep: 120`.
- Node: rounded card with icon by kind (host, external), label, and an "Isolate" button on hover.
- Edge: label is `action`. Styles by state:
  - verified, survived: solid, neutral
  - unverified: dashed, muted, with a small "unverified" tag
  - vanished (after diff): dashed, red, 40 percent opacity, still clickable
  - appeared (after diff): solid, green
- Edge click opens the evidence panel. Edge hover shows a "Block" button.
- Nodes carry the same three diff statuses as edges. A vanished node (isolated, or no longer
  part of the chain) is still drawn, faded, so the user sees what they removed. Appeared nodes
  are drawn solid with a green ring.

### Evidence panel

Header: `source -> target`, action, description. Then one row per citation: id, timestamp,
source, target, type, detail, and a check or cross for each of the two checks. Unverified edges show the
reason in one line: "Event E-0119 names administrator, not WKSTN-042."

### Intervention flow

1. Click Isolate or Block. The button shows a spinner. The rest of the UI stays interactive
   except further interventions, which queue behind the in-flight call.
2. On success, the new chain is parsed with zod, validated, diffed against the previous
   validated chain (nodes and edges), and rendered as a `DiffedChain`.
   A one-line banner reads: "Removed 14 events. 3 edges vanished, 2 survived, 1 appeared."
3. On failure, a banner shows the error and the previous graph stays.
4. Reset reloads the cached analysis and clears removals.

### Answer key

A slide-over listing the story steps and the attack event ids. Ids that are cited by the
current chain are marked. This is how a non-expert reviewer checks the model.

## Scenarios (already generated by the skill)

### attack-chain-01: "Finance file-server exfiltration" (the demo scenario)

500 events between 07:31Z and 17:29Z on 2026-09-05. 16 planted attack events between 09:14Z
and 09:46Z, ids scattered from `E-0095` to `E-0137`. Assets involved: `jsmith`, `administrator`,
`WKSTN-042`, `DC-01`, `FILESRV-01`, `203.0.113.47` (command and control), `198.51.100.22`
(exfiltration).

| Step | Events | Edge the model should draw |
|---|---|---|
| External RDP logon as jsmith | E-0095 | `203.0.113.47 -> WKSTN-042` |
| Encoded PowerShell from Outlook, C2 beacon, discovery, LSASS dump | E-0096, E-0102, E-0107 / E-0097 | `jsmith -> WKSTN-042`, `WKSTN-042 -> 203.0.113.47` |
| Pass-the-hash to the domain controller | E-0111 | `WKSTN-042 -> DC-01` |
| Admin logon and SMB to the file server | E-0115, E-0117 | `WKSTN-042 -> FILESRV-01` |
| Remote execution, Finance and HR reads, staging, log clearing, cleanup | E-0119, E-0122, E-0124, E-0125, E-0136, E-0137 | `administrator -> FILESRV-01` |
| 480MB exfiltration, completion signal | E-0129, E-0132 | `FILESRV-01 -> 198.51.100.22`, `FILESRV-01 -> 203.0.113.47` |

Expected chain: 7 nodes, 7 or 8 edges.

**The hero moment.** Isolating `FILESRV-01` removes E-0115 through E-0137 except E-0111. The
collection and exfiltration edges vanish. The credential-theft path survives:
`203.0.113.47 -> WKSTN-042 -> DC-01`, with the beacon still running. The remaining evidence
says the attacker still has a foothold and domain administrator credentials. Isolating
`WKSTN-042` instead removes the initial access, the beacon, the credential dump, and both
lateral logons; only the `administrator -> FILESRV-01` activity and the exfiltration remain,
which the model should still connect because the events are in the same window.

The generator's own note agrees: "Removing FILESRV-01 should collapse the exfiltration edges
but leave the credential-theft path (WKSTN-042 -> DC-01) intact."

### benign-lookalike-02: "Busy IT night, no attack" (optional in the UI)

500 events, 16 lookalike events that each resemble a technique but share no pivot host,
credential, or destination. The correct chain is empty or a few unverified fragments. The
answer key carries a `why_benign` line per lookalike. Data exists; wiring a scenario switcher
is an optional task after the cut line.

There are no self-loop events in either scenario, so validation has no special case.

## Claude Code skill: generate-scenario (exists)

`.claude/skills/generate-scenario/` already contains `SKILL.md` and `generate.py`. It is a
deterministic Python generator with fixed seeds per scenario, so regeneration is byte-identical.
It asserts its own invariants at the end of every run: 500 unique sequential ids, sorted
timestamps, the four allowed types, every seeded event spanning two distinct assets, and
attacker IPs absent from noise.

Two changes are needed, both in the first task: the default output path moves from
`src/main/resources/scenarios/` to `data/scenarios/`, and the SKILL.md run instructions are
updated to match. Nothing else about the generator changes.

`scripts/analyze.py <scenario-id>` imports `api.analysis.analyze`, runs it on the full event
set, and writes `analysis.json` beside the generated files. This is the only step that calls
the model at build time.

## Vercel deployment

- `vercel.json`:
  ```json
  {
    "functions": { "api/**/*.py": { "maxDuration": 60, "includeFiles": "data/**" } },
    "rewrites": [{ "source": "/api/(.*)", "destination": "/api/index" }]
  }
  ```
- `requirements.txt` at the repo root: `fastapi`, `anthropic`, `pydantic`.
- Vercel detects Vite from `package.json` and builds `dist/`. `prebuild` copies
  `data/scenarios` to `public/scenarios`.
- Environment variable `ANTHROPIC_API_KEY` set in the Vercel project. Never in the repo.
- Local development: `uvicorn api.index:app --port 8000` and `npm run dev` with a Vite proxy
  from `/api` to `localhost:8000`. `vercel dev` also works once the CLI is installed.
- Deployment is push to `main` with the Vercel GitHub integration, or `vercel --prod`.

Verify on the first deploy: that `includeFiles` makes `data/scenarios` readable from the
function, and that `maxDuration: 60` is accepted on the account's plan. If either fails, the
fallback is to copy scenario JSON into `api/scenarios/` and lower `maxDuration` to the plan
maximum.

## Constitution check

| Principle | How the plan satisfies it |
|---|---|
| I. Evidence before conclusions | `validate.ts` gates every edge; unverified edges render dashed. |
| II. One intervention mechanism | Both buttons produce `removed_event_ids`; one endpoint, one prompt. |
| III. Real re-analysis | `/api/analyze` calls the model. Only the first screen is cached. |
| IV. Honest wording | Prompt forbids the banned words; no score field exists in the schema. |
| V. Novice first | Left-to-right layout, plain-English labels, evidence panel, answer key. |
| VI. Scope discipline | Cut order in tasks.md. Diff and summary go before live re-analysis. |
| VII. Clean provenance | Fresh generator, prompt, schema, and UI. Nothing imported from prior work. |

## Risks specific to this plan

- **Vercel Python cold start** adds 1 to 3 seconds to the first live call. Acceptable. The
  health check on page load warms the instance.
- **Model returns different node ids than the events use.** External assets carry labels such
  as `151.101.1.140 (fastly-cdn)` and the model may drop the label. Prompt says names must be
  copied verbatim. Validation catches the rest, and the evidence panel shows why.
- **Model collapses users into hosts.** It may draw `WKSTN-042 -> FILESRV-01` and cite
  `administrator -> FILESRV-01` events. Those citations fail the endpoint check and the edge
  shows as unverified, which is the correct signal. The prompt states that users are assets
  and that an edge's endpoints must match the cited events' source and target.
- **Refusal on security content.** Log analysis is defensive and should not trigger a refusal.
  The server handles `stop_reason == "refusal"` and returns `model_refused` so the UI can say
  so instead of hanging.
